A declarative pipeline: describe a domain once as JSON, get a complete referentially-consistent dataset materialised into PostgreSQL, CSV, JSON, Parquet and a live REST API at the same time.

The engineering that matters only becomes visible at scale. The data that exhibits scale is held by organisations that will not release it. So the ability to practise at scale is gated by employment. Making volume a parameter rather than a property of a handed-over dataset removes that gate.

the finding that matters most

Three load strategies, three different regimes

The original pipeline sent one INSERT per row: about 85,400 sequential network round trips. The problem was never bandwidth. 85,400 rows is 16.5 MB. The problem was 85,400 sequential waits, at roughly 0.3 seconds each.

Splitting each strategy's time into waiting for the network and actually sending data shows these are not three points on one curve:

Two consequences follow

The large multiple is rowwise → execute_values, which removes the waiting. COPY then buys a further 2.19×, which is real but an order of magnitude smaller.

And parallel loading should be roughly flat: COPY is already 92% bandwidth-bound, so splitting one uplink across N connections cannot create bandwidth. That prediction is recorded as open work rather than quietly skipped.

At 854 rows both collapse to 5 round trips, so COPY's stream setup has nothing to amortise and it loses. A benchmark run at one scale would get this backwards.

The 7.21-hour row-at-a-time figure is projected: 854 round trips were measured at 259.61s, giving 0.304s each, and 85,400 round trips follow from the row count. A full-scale run would take most of a working day to produce a number already fixed by two measured quantities.

generation

An accidentally quadratic foreign-key lookup

Resolving a foreign key rebuilt the entire list of candidate parent ids on every single field call, for a result that never changes within a table. About two billion dictionary probes per run. Memoizing it produces byte-identical output, verified across all six tables and all 49 fields.

tablerowsbeforeafterrelativespeedup

The headline multiple is not the interesting part. The speedup tracks rows × parent-rows, and the three tables with no meaningful foreign-key load are flat. That pattern is what separates the right fix from a lucky one.

veracity

Structurally valid is not the same as believable

Every foreign key resolved, every type matched, every unique column was unique — and every user was an infant, half the orders predated the accounts that placed them, and no order total matched its line items. A query planner never sees data shaped like that, so it teaches you nothing.

measured at full scalebeforeafter

Four of these were already in the project's defect register. Three were not, and the worst is unit_price: reconciling order totals while line prices bear no relation to the product being bought is arithmetic over noise. It yields a dataset that is internally consistent and still describes impossible orders. Every rule is driven by field names and the foreign-key graph, never hardcoded table names, which is what keeps the pipeline declarative.

storage

Why columnar is the format analytical tools use

The same table — products, 20,000 rows across 11 fields — written to all three file destinations. Read timings are best-of-five after a warm-up, so they measure I/O rather than library import cost.

A row-oriented file reads every byte to reach one column. A columnar file reads only the chunks it needs. That is the whole argument.

The first run of this benchmark reported Parquet reads as slower than CSV, 0.52s against 0.12s. That was pyarrow's first-import cost, not I/O. Warming the libraries reversed the result by a factor of 24. It is recorded as a correction, because the method matters as much as the numbers.

What this does not do

  
    
    
  • 
      It is not a privacy tool. It does not learn a distribution
      from real data and emit a private imitation. There is no real data anywhere
      in the process.
    
    • 
    
  • 
      No GPU path, deliberately. An RTX 4050 is available and
      unused. Faker is pure Python over CPython's RNG with no CUDA path; a first
      CuPy call initialises the CUDA context in 0.5–2 seconds, more than the
      entire CPU cost of every numeric column combined; and cuDF has no native
      Windows build. The run is bandwidth-bound anyway. The honest prediction,
      recorded before building it, is that a GPU path would be slower at
      this scale.
    
    • 
    
  • 
      Parallel loading is implemented but unmeasured, and
      predicted to be flat.
    
    • 
    
  • 
      The API serves only orders. Response models
      are hand-written, so a second api table is loaded but not
      exposed.
    
    • 
    
  • There is no CI.
    • 
    
  • 
      A coursework demonstrator, not production ELT. Correctness, measurement and
      clarity were the goals; multi-node horizontal scale was not.
