What to try

Switch the load strategy and watch the clock change. Row-at-a-time sends one INSERT per row, which is 85,400 sequential network round trips at roughly three tenths of a second each. The replay compresses it, because the real thing takes over seven hours.

Something the measurement exposed

Of the 35.03 s write step, only 17.39 s is loading. The rest is five separate connection handshakes, one per table, because the loader opens its own connection when none is passed in. Reusing one would roughly halve that step. Listed as open work rather than quietly fixed in the prose.

One dataset, five destinations

Foreign keys survive leaving the database because every sink is materialised from a single in-memory dataset rather than generated per sink. The id a CSV row carries is the same object the PostgreSQL parent row carries. Select any stage below.

PostgreSQL

Proven by the server, not asserted

Constraints are created after the bulk load, so PostgreSQL validates every generated reference in one sequential pass. If generation were wrong, the constraint is refused and the offending row named.

Data that is believable, not merely valid

Honest limits

      
    
        
  • Not a privacy tool. It does not learn a distribution from real data and emit a private imitation. There is no real data anywhere in the process.
    • 
        
  • No GPU path, on purpose. Faker is pure Python over CPython's RNG with no CUDA path; a first CuPy call initialises the CUDA context in 0.5–2 seconds, more than the entire CPU cost of every numeric column combined; cuDF has no native Windows build. The run is bandwidth-bound anyway. The prediction, recorded before building it, is that a GPU path would be slower at this scale.
    • 
        
  • The loader opens one connection per table. Roughly 17 of the 35-second write step is handshakes. Reusing a connection is open work.
    • 
        
  • Parallel loading is implemented but unmeasured, and predicted to be close to flat.
    • 
        
  • The API serves only orders. Response models are hand-written, so a second api table is loaded but not exposed.
    • 
        
  • There is no CI.
    •
