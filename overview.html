Synthetic data at scale, for everyone outside the companies that own it

Describe a domain once as JSON. Get a complete, referentially-consistent dataset materialised into PostgreSQL, CSV, JSON, Parquet and a live REST API at the same time – at whatever volume you ask for.

Why it matters. The engineering that matters only shows up at scale. The data that has scale belongs to companies that will not release it. So practising at scale is gated by employment. Making volume a parameter removes the gate.

01 Mechanism
Fig. 1. Select any stage for what it does and what it cost in the measured run. Two tables land in two places each, which is where the integrity claim is actually tested.

One dataset, five destinations, one set of ids

Foreign keys stay valid across destinations because every sink is materialised from a single in-memory dataset rather than generated per sink. The id a CSV row carries is the same object the PostgreSQL parent row carries.

Each dot is a batch moving to its destination.
02 Load path
Projection method. 854 round trips were measured at 259.61 s, giving 0.304 s each. 85,400 round trips follow from the row count. A full-scale row-at-a-time run would take most of a working day to produce a number already fixed by two measured quantities, so it was not performed.

Three strategies, three different regimes

The original pipeline sent one INSERT per row: about 85,400 sequential round trips. Bandwidth was never the problem. 85,400 rows is 16.5 MB. The problem was 85,400 sequential waits, at roughly three tenths of a second each.

03 Generation
Why log scale. The per-table times span 0.05 s to 62.93 s. On a linear axis every row but one would be invisible.
Byte-identical. Memoizing is safe because tables generate in topological order, so the cached list is the same list in the same order and the RNG draw is unchanged. Verified across all six tables and all 49 fields.

An accidentally quadratic foreign-key lookup

Resolving a foreign key rebuilt the entire list of candidate parent ids on every single field call, for a result that never changes within a table. About two billion dictionary probes per run.

04 Veracity
Declarative, still. Every repair rule is driven by field names and the foreign-key graph, never by hardcoded table names. A column called cost is kept below one called price without any ecommerce-specific code.

Structurally valid is not the same as believable

Every foreign key resolved, every type matched, every unique column was unique. And every user was an infant, half the orders predated the accounts that placed them, and no order total matched its line items. A query planner never sees data shaped like that.

05 Storage
A correction. The first run of this benchmark reported Parquet reads as slower than CSV, 0.52 s against 0.12 s. That was pyarrow's first-import cost, not I/O. Warming the libraries reversed it by a factor of 24.

What columnar storage actually buys

The same table, products at 20,000 rows across 11 fields, written to all three file destinations. Read timings are best-of-five after a warm-up, so they measure I/O rather than library startup.

06 Integrity
Checked both ways. An integration test reads foreign keys out of exports/csv/reviews.csv and resolves them against rows in PostgreSQL. A user_id sitting in a flat file has to name a real database row.

Foreign keys that survive leaving the database

Constraints are created after the bulk load, so PostgreSQL validates every generated reference in one sequential pass. If generation were wrong, the constraint is refused and the offending row named. The claim is proven by the server, not asserted by its author.

What this does not do

      
    
        
  • 
          It is not a privacy tool. It does not learn a distribution from
          real data and emit a private imitation. There is no real data anywhere
          in the process.
        
    • 
        
  • 
          No GPU path, on purpose. An RTX 4050 sits unused. Faker is pure
          Python over CPython's RNG with no CUDA path; a first CuPy call
          initialises the CUDA context in 0.5–2 seconds, more than the
          entire CPU cost of every numeric column combined; cuDF has no native
          Windows build. The run is bandwidth-bound anyway. The prediction,
          recorded before building it, is that a GPU path would be
          slower at this scale.
        
    • 
        
  • Parallel loading is implemented but unmeasured, and predicted to be flat.
    • 
        
  • 
          The API serves only orders. Response models are
          hand-written, so a second api table is loaded but not
          exposed.
        
    • 
        
  • There is no CI.
    • 
        
  • 
          A coursework demonstrator, not production ELT. Correctness,
          measurement and clarity were the goals. Multi-node horizontal scale
          was not.
