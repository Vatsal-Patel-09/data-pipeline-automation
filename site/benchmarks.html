    Measured, not claimed

    Every figure comes from a harness committed in the repository, run with nothing else on the machine and repeated. One number is projected rather than measured, and says so. Two earlier measurement mistakes are recorded at the bottom, because the method matters as much as the numbers.

    Generation, per table, full scale

    Resolving a foreign key rebuilt the entire list of candidate parent ids on every single field call, for a result that never changes within a table. About two billion dictionary probes per run. Memoizing it is byte-identical output, verified across all six tables and all 49 fields.

    tablerowsbeforeafterseconds, log scalegain

    ● before   ● after. The gain tracks rows × parent-rows, and the three tables with no real foreign-key load sit still. That pattern separates the right fix from a lucky one.

    Data that is believable, not merely valid

    Every foreign key resolved, every type matched, every unique column was unique. And every user was an infant, half the orders predated the accounts that placed them, and no order total matched its line items. A query planner never sees data shaped like that.

    propertybeforeafter

    Every repair rule is driven by field names and the foreign-key graph, never by hardcoded table names. A column called cost is kept below one called price with no domain-specific code, which is what keeps the pipeline declarative.

    Corrections

    • A contended baseline, inflated about 2×. The first generation baseline was reported as 207.5 s with the fixed version at 17.5 s, an 11.9× speedup. Both were measured while other work ran on the same machine. Uncontended and repeated, the real figures are 101.24 s and 10.06 s, for 10.1×.
    • A cold-start artifact, reversed by 24×. The first format benchmark reported Parquet reads at 0.52 s against CSV’s 0.12 s. That was pyarrow’s first-import cost, not I/O. Warmed and repeated, Parquet reads in 0.022 s against 0.081 s.
